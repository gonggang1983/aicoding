# OryxOS 当前实现情况与后续功能优先级

## 一、当前结论

当前 `code/` 目录已经完成的是 **OryxOS 最小可运行代码工程初始化**，也就是：

> 工程骨架已完成，最小 mock 主链路已完成；真实 LLM、完整 ReAct、真实 Tool 调用、MCP、调度、企业治理等能力还需要后续继续实现。

从 `docs/DemandAnalysis.md` 的核心需求来看，下一步最应该优先做的是：

> **真实 LLM Provider + ReAct Loop + HTTP Tool + CLI 天气 Demo**。

这条链路是 OryxOS 从“工程骨架”走向“真正能干活的 Agent Runtime”的最短闭环。

## 四、对照需求文档后的优先级建议

### 最推荐先做的功能

对比 `docs/DemandAnalysis.md`，下一步最应该先做：

```text
真实 LLM Provider + ReAct Loop + HTTP Tool + CLI 天气 Demo
```

这对应需求文档第一周主线：

```text
对接 LLM + ReAct 循环 + HTTP Tool + CLI
```

也就是先跑通：

```text
用户输入任务
  → Agent 读取 AGENT.md
  → 组装 Prompt
  → 调用真实 LLM
  → LLM 决定调用 http_get
  → OryxOS 执行 HTTP Tool
  → Tool 结果回填给 LLM
  → LLM 输出最终回答
```

这条链路一旦跑通，OryxOS 就从“工程骨架”变成了“真正能干活的 Agent Runtime”。

---

## 五、建议第一批功能拆分

### 任务 1：接入真实 LLM Provider

先不要一次接很多家，建议二选一：

1. **DeepSeek**：通常 OpenAI-compatible，接入简单。
2. **Kimi**：国内常见，也适合作业展示。

建议先接 DeepSeek，因为它可以用 OpenAI-compatible API 风格，工程实现更快。

需要做：

- 增加 `OpenAiCompatibleChatProvider`
- 配置：
  - base URL
  - API key
  - model
- 从环境变量读取 key，例如：

```yaml
oryxos:
  providers:
    deepseek:
      base-url: ${DEEPSEEK_BASE_URL:https://api.deepseek.com}
      api-key: ${DEEPSEEK_API_KEY:}
      model: ${DEEPSEEK_MODEL:deepseek-chat}
```

验收：

```bash
DEEPSEEK_API_KEY=xxx java -jar target/oryxos-0.1.0-SNAPSHOT.jar chat --profile demo --message "你好"
```

能返回真实模型回复。

---

### 任务 2：定义 OryxOS Tool Call JSON 协议

不要一开始就依赖复杂 Function Calling。可以先让模型按固定 JSON 格式输出。

工具调用格式：

```json
{
  "type": "tool_call",
  "tool": "http_get",
  "arguments": {
    "url": "https://api.example.com/weather?city=beijing"
  }
}
```

最终回答格式：

```json
{
  "type": "final",
  "content": "北京今天晴，适合出门。"
}
```

需要做：

- `ReactLoop` 判断模型输出是 `tool_call` 还是 `final`
- 增加 `ToolCallParser`
- 增加 `ReactStep`
- 失败时让模型重新输出合法 JSON

验收：

- 模型能输出工具调用 JSON
- OryxOS 能识别工具名和参数

---

### 任务 3：把 HTTP Tool 接入 ReAct Loop

当前 `http_get` 已经实现，但还没有被 LLM 自动调用。

要补：

```text
ReactLoop
  → 解析 tool_call
  → ToolRegistry.find(toolName)
  → tool.invoke(arguments)
  → 记录 tool_invocations
  → 把 ToolResult 作为 observe 消息回填给 LLM
  → 继续下一轮
```

验收：

用户输入：

```bash
oryxos chat --profile weather --message "查一下北京天气"
```

Agent 至少能完成：

1. LLM 决定调用 `http_get`
2. OryxOS 执行 HTTP 请求
3. LLM 根据 HTTP 结果生成自然语言回复

---

### 任务 4：做一个 `weather` Agent Demo

新建：

```text
.oryxos/agents/weather/AGENT.md
```

配置：

```yaml
---

```

验收：

```bash

```

## 七、暂时不建议先做的功能

以下功能虽然在文档里出现，但不适合现在马上做：

### 1. Web 管理台

当前核心 Agent Runtime 还没跑通真实 LLM，先做 UI 容易变成空壳。

### 2. MCP

MCP 要在 ToolRegistry、ReAct、Tool Call 协议稳定后接入，否则会反复改。

### 3. 定时任务 AgentScheduler

定时任务本质只是第三触发源，应该等手动触发链路稳定后再做。

### 4. 多租户 / SSO / RBAC

这是企业治理层，文档也放在扩展阶段，不是当前核心阶段最短链路。

### 5. 分布式

当前还在单机运行时内核阶段，先把单机做扎实。
