# OryxOS 需求分析

> 本文基于 `docs/DemandAnalysis.md`、`docs/TechnicalSolution.md`、`docs/VisionAndRoadmap.md` 重新整理，目标是回答：OryxOS 要解决什么问题，用户是谁，核心阶段必须交付什么，扩展阶段继续补什么。

---

## 1. 项目定位

OryxOS 是一个面向企业场景的 **Agent Harness OS / Agent OS**。它部署在企业自己的服务器、虚拟机或 K8s 集群中，作为统一底座运行多个业务 Agent。

OryxOS 的目标不是替企业写一个固定 Agent，而是提供一套公共运行环境，让企业可以低成本定义、运行和管理很多 Agent：

- 运维 Agent。
- 客服 Agent。
- HR Agent。
- 销售 Agent。
- 法务 Agent。
- 知识管理 Agent。
- 研发协作 Agent。

一句话：

> **让业务方用自然语言和 Markdown 定义 Agent，让底座负责模型、工具、记忆、沙箱、审计、调度和对外服务。**

## 2. 用户与角色

### 2.1 平台方 / 运维方

负责部署和维护 OryxOS：

- 配置 Provider。
- 管理工具白名单。
- 接入 MCP server。
- 管理通知渠道。
- 查看审计和运行状态。
- 未来接入 SSO / RBAC / 多租户。

他们关心稳定性、安全、审计、成本和运维集成。

### 2.2 Agent 作者 / 业务专家

负责定义某个业务 Agent：

- 写 `AGENT.md`。
- 绑定可用 Tool。
- 绑定 Skill。
- 配置定时任务。
- 描述任务目标和输出格式。

他们最好不写 Java 代码，只用 Markdown 和少量 YAML 完成 Agent 定义。

### 2.3 Tool / Connector 开发者

负责把企业系统接进 OryxOS：

- 写 MCP server。
- 写 Java `@Tool` Bean。
- 接 ERP / CRM / CMDB / 知识库 / 监控系统。

他们关心扩展接口稳定、协议标准、测试方便。

### 2.4 最终用户

通过 CLI、Web、IM 或业务系统使用 Agent：

- 问问题。
- 发任务。
- 接收定时报告。
- 审批危险动作。

他们关心响应质量、速度和可信度。

## 3. 核心问题

OryxOS 要解决的不是“模型会不会聊天”，而是企业 Agent 进入生产前的工程问题。

### 3.1 定义成本高

没有底座时，做一个业务 Agent 往往要从零写：

- 模型调用。
- 对话历史。
- 工具调用。
- Function Calling。
- 错误处理。
- 审计。
- 沙箱。
- API。

每做一个 Agent 都重复造轮子。

OryxOS 的需求是：

> 一个目录 = 一个 Agent。业务方写 `AGENT.md` 和必要资源即可上线。

### 3.2 企业不敢把 Agent 放进生产

Agent 会调用工具，可能读文件、跑命令、访问外部 API。没有沙箱和审计，企业不敢让它碰生产环境。

OryxOS 必须提供：

- 文件路径白名单。
- Shell 命令白名单。
- HTTP 域名白名单和 SSRF 防护。
- Tool 调用审计。
- LLM 调用审计。
- 未来 HITL 审批。

### 3.3 数据不能出企业

严监管企业不能把核心业务数据交给外部 SaaS Agent 平台。

OryxOS 必须：

- 可私有部署。
- 数据留在企业自己的数据库和文件系统。
- 支持企业自有模型或 OpenAI-compatible 本地推理服务。
- 凭证走环境变量或企业密钥体系。

### 3.4 一群 Agent 难以统一管理

单个 Agent demo 容易，一群 Agent 的生命周期、工具权限、记忆、审计和成本治理才是难点。

OryxOS 必须逐步提供：

- Agent 生命周期管理。
- 多 Agent 并存。
- 定时任务。
- 执行历史。
- Web 管理台。
- 未来多租户、RBAC、成本看板和 Agent 团队协作。

## 4. 北极星公式

OryxOS 的产品需求可以压缩成一个公式：

```text
自然语言(md) + Memory + Tool + MCP + Skill + 知识库 + Notify = 一个能干活的 Agent
```

各要素的需求如下：

| 要素 | 需求 |
| --- | --- |
| 自然语言(md) | 用 `AGENT.md` 定义 Agent，frontmatter 配置怎么跑，正文描述做什么 |
| Memory | 跨会话保留用户偏好、项目背景和历史决策 |
| Tool | 内置文件、Shell、HTTP、时间、JSON 等基础工具 |
| MCP | 接社区和企业自有工具，降低扩展成本 |
| Skill | 沉淀可复用指令、格式、流程和专家经验 |
| 知识库 | 让 Agent 检索企业内部文档并给出引用 |
| Notify | 让 Agent 主动推送结果，支持定时任务闭环 |

当前最关键的未补能力是知识库；它决定 Agent 能否真正理解企业业务资料。

## 5. 核心阶段功能需求

核心阶段目标：先把单机运行时内核做扎实，让一个 OryxOS 实例能运行多个 Agent。

### 5.1 工作区初始化

通过 `oryxos init` 创建 `.oryxos/`：

```text
.oryxos/
├── agents/
├── skills/
├── memory/
├── output/
├── logs/
├── mcp_servers.yaml
├── AGENTS.md
├── SOUL.md
└── USER.md
```

需求：

- 幂等，不覆盖用户已有文件。
- 创建默认目录和 Bootstrap 文件。
- 为 Agent / Skill / Memory / MCP 留好结构。

### 5.2 Agent 定义

需求：

- 一个目录就是一个 Agent。
- `.oryxos/agents/<name>/AGENT.md` 包含 frontmatter 和正文。
- frontmatter 派生成运行时 `Profile`。
- 正文由 `ContextLoader` 注入 system prompt。
- Skill 不是 Tool，不进 `ToolRegistry`。

### 5.3 Provider

需求：

- 支持 OpenAI-compatible Provider。
- 支持 deepseek、qwen、kimi、openai、本地 vLLM 等按配置接入。
- Provider name 到 ChatModel 必须显式映射，不能靠类型扫描。
- LLM 调用写入 `llm_calls`。

### 5.4 ReAct Loop

需求：

- 自实现 ReAct 循环。
- 不使用 Spring AI 自动工具执行。
- 每轮组装 prompt、调用 LLM、解析 tool call、执行工具、回填结果。
- 最大迭代次数默认 10，可配置。
- Tool 执行失败以 ToolResult 形式回填，让模型下一轮决策。

### 5.5 Memory

需求：

- 会话记忆持久化。
- 长期记忆可读写。
- 提供 `save_memory` / `recall_memory`。
- 默认 Markdown，人可读、可审计。
- 可切换 SQLite / Mem0 后端。
- 核心阶段不做复杂自动抽取和知识图谱。

### 5.6 Tool / MCP / Sandbox

需求：

- `ToolRegistry` 统一注册内置 Tool、MCP Tool、Java `@Tool`。
- 内置工具至少覆盖文件、Shell、HTTP、Memory、Notify。
- MCP Client 支持 stdio / HTTP-SSE 连接。
- 文件、Shell、HTTP 都必须先过 `Sandbox.enforce()`。
- 沙箱默认 fail closed。

### 5.7 Session / Audit

需求：

- Session 跨重启恢复。
- 对话历史 JSON 序列化入 SQLite。
- `tool_invocations` 和 `llm_calls` 核心阶段就写入。
- 定时任务执行历史也要留痕。

### 5.8 Web Service

需求：

- 提供 REST API。
- 覆盖会话管理、Agent 调用、Agent 管理、Provider 管理、Tool 查询、Skill 管理、MCP 管理、沙箱白名单、定时任务、工作区文件浏览。
- 核心阶段可假设内网无认证。
- 扩展阶段补认证、RBAC、SSE、限流。

### 5.9 CLI

需求：

- `oryxos init`
- `oryxos status`
- `oryxos chat`
- `oryxos serve`
- `oryxos gateway`
- `oryxos profile list/create/show/delete`
- `oryxos provider list`
- `oryxos tool list`
- `oryxos session list`

## 6. 扩展阶段功能需求

### 6.1 知识库

这是近期最重要的扩展：

- 文档导入。
- 文档切分。
- embedding。
- 向量检索。
- `retrieve_knowledge` Tool。
- `knowledge: [name]` 或等价绑定方式。
- 引用来源可追溯。

### 6.2 分布式

- SQLite → PostgreSQL / MySQL。
- 实例注册和心跳。
- DB 抢锁调度。
- 多副本部署。
- 无状态实例。

### 6.3 多 Agent / Flow / A2A

- Flow 声明式编排。
- 子 Agent 委托。
- A2A 协议。
- Agent 团队：协调者 + 专家 + 评审。
- 任务发布：一句话 → 拆解 → 组织团队 → 交付结果。

### 6.4 企业治理

- SSO。
- RBAC。
- 多租户。
- Tool Policy。
- 成本看板。
- 审计 UI。
- HITL 审批。
- OpenTelemetry。

### 6.5 多渠道 / 多模态

- 飞书 / 企业微信 / 钉钉。
- Slack / Telegram / Discord / Teams / Email。
- WebSocket / SSE。
- 浏览器自动化。
- 视觉、图像、TTS、实时语音。

## 7. 非功能需求

### 7.1 安全

- 默认最小权限。
- Tool 必须受沙箱约束。
- 凭证不得明文写入 Agent 文件。
- 审计 day-one 落库。
- 对外发送、Shell、支出、越权改动等未来应接 HITL。

### 7.2 可靠性

- 单个 Tool 失败不能拖垮 ReAct 循环。
- 定时任务失败不能拖垮调度器。
- Provider 故障核心阶段直接报错，扩展阶段支持 fallback。
- Session 和审计不能丢。

### 7.3 可运维性

- 支持 `java -jar` 单体部署。
- 提供 CLI 和 Web 管理台。
- 提供健康检查、结构化日志。
- 扩展阶段提供 Prometheus 和 tracing。

### 7.4 易用性

- 业务方定义 Agent 尽量不写代码。
- Agent 目录可 GitOps 管理。
- Skill / MCP / Tool 可复用。
- 管理台能查看运行状态和失败原因。

## 8. 验收场景

### 8.1 每日天气 Agent

到点自动查天气，生成穿搭建议，并通知到群。

覆盖：

- Scheduler。
- ReAct。
- HTTP Tool。
- Notify。
- Audit。
- Session 查询。

### 8.2 每日科技日报 Agent

按用户记忆偏好汇总科技新闻，并按 Skill 约束格式输出。

覆盖：

- Memory。
- Skill 渐进式披露。
- MCP / HTTP。
- Notify。
- 定时任务。

### 8.3 GitHub 日报 Agent

Agent 目录内带脚本，定时运行脚本获取 GitHub 数据，再由 LLM 总结。

覆盖：

- Shell Tool。
- Agent scripts。
- Sandbox。
- Tool audit。

---

## 9. 需求结论

OryxOS 的核心需求不是“能调用大模型”，而是：

> 企业可以用一套 Java 原生、私有可审计的底座，把多个业务 Agent 低成本定义出来、安全运行起来、统一管理起来，并逐步走向知识库、分布式、多租户和多 Agent 协作。

核心阶段要把“一个 Agent 能可靠跑起来”做扎实；扩展阶段要把“企业敢让一群 Agent 跑起来”做完整。
