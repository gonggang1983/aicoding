# OryxOS 业界调研

> 本文基于 `docs/IndustryResearch.md`、`docs/oryxos.md`、`docs/VisionAndRoadmap.md` 重新整理，目标是回答：业界已经在 Agent OS 方向做了什么，为什么 Java 生态还缺这一层，以及 OryxOS 应该把自己锚定在哪里。

---

## 1. 核心结论

OryxOS 要做的不是“又一个更强的 Agent”，而是企业自己的 **Agent Harness OS / Agent OS**：一套装在企业自己服务器或 K8s 上的运行底座，用来运行、管理、审计和协同一群业务 Agent。

当前业界已经证明了 Agent OS 这个方向的价值：

- 个人和开发者市场需要一个“装上就能跑 Agent”的本地底座。
- 企业市场需要一个“私有、可控、可审计、能接入现有 IT 系统”的统一底座。
- Node.js 和 Python 生态已有代表性项目，但 Java 生态在 Agent OS 这一层明显缺位。

OryxOS 的机会在于：

> **用 Java / Spring 生态补齐企业 Agent OS 这一层，让严监管企业能在自己的基础设施上运行一群 Agent，数据不出域、行为可审计、工具可控、能力可沉淀。**

---

## 2. Agent OS 是什么

Agent OS 是运行和管理 AI Agent 的底座。它不直接等同于某个 Agent，也不只是一个 LLM SDK，而是模型外面那层让 Agent 能真正“做事”的运行骨架。

一个合格的 Agent OS 至少包含：

1. **Agent 生命周期管理**：创建、加载、更新、删除、归档、定时运行多个 Agent。
2. **统一模型接入**：屏蔽 DeepSeek、通义、Kimi、OpenAI、Anthropic、本地 vLLM 等 Provider 差异。
3. **ReAct 执行循环**：驱动 reason → act → observe，让模型能决定何时调用工具。
4. **工具体系**：内置文件、Shell、HTTP、通知、记忆工具，也能接 MCP server 和 Java `@Tool`。
5. **记忆系统**：会话记忆、长期记忆、未来的语义记忆和主体画像。
6. **沙箱与审计**：所有工具调用有白名单、安全边界和结构化审计记录。
7. **对外入口**：CLI、REST API、定时任务，未来扩展 IM / Email / WebSocket / Voice Channel。

Agent runtime 让一个 Agent 跑起来；Agent OS 让一群 Agent 在企业里被统一管理起来。

## 3. 业界代表项目

### 3.1 OpenClaw

OpenClaw 代表的是个人和开发者优先的 Agent OS 路线：

- Node.js 实现。
- 社区活跃，渠道丰富，skill 生态大。
- 上手快、可玩性强。
- 安全治理相对薄弱，公开市场和第三方 skill 带来供应链风险。

OpenClaw 证明了“Agent OS 作为本地运行底座”有强需求，但它更偏个人和小团队，不是严监管企业可以直接放心使用的生产底座。

### 3.2 Hermes Agent

Hermes Agent 代表的是工程化、个人到团队级的 Agent OS 路线：

- Python 实现。
- 强调持久记忆、自我进化 skill、安全扫描、用户隔离。
- 比 OpenClaw 更稳，更接近企业需求。
- 但真正的企业级多租户、SSO、RBAC、完整审计和成本治理仍不是 day-one 核心。

Hermes 证明了 Agent OS 需要记忆、自我演进和安全边界，但它仍然不是 Java 企业栈原生的运行底座。

## 4. 业界空白

### 4.1 企业级治理仍是空白

现有开源 Agent OS 大多从个人和小团队出发，企业真正需要的治理能力仍缺：

- 多租户隔离。
- SSO / OIDC / SAML。
- RBAC 权限模型。
- Tool Policy。
- 成本与 token 看板。
- 审计回放与 SIEM 导出。
- HITL 审批。

这些不是 UI 上再加几个按钮就能补齐的功能，而是需要从底座架构里 day-one 设计。

### 4.2 企业 IT 深度集成不足

企业 Agent 真正有价值，不是能闲聊，而是能接企业自己的系统：

- ERP / CRM / OA / CMDB。
- Prometheus / Grafana / 日志系统。
- Jira / GitHub / GitLab / Confluence。
- 飞书 / 企业微信 / 钉钉。
- 内网知识库和审批系统。

这类系统在企业里大量是 Java / Spring 生态，跨语言胶水成本很高。

### 4.3 Java 生态缺位

Java 生态已有 Spring AI、Spring AI Alibaba、LangChain4j 等框架，但这些是“写 AI 应用的库”，不是“装上就能运行和管理一群 Agent 的底座”。

Java 企业生态成熟完整：

- Spring Boot / Spring MVC。
- Spring Data JPA。
- Nacos / Sentinel / SkyWalking / Arthas。
- Prometheus / Grafana。
- 企业既有 Java SDK 和治理流程。

但 Agent OS 这一层是空的。OryxOS 要补的就是这块生态断层。

## 5. OryxOS 的定位

OryxOS 的定位可以收成一句话：

> **OryxOS 是企业私有部署的 Java Agent Harness OS：一个目录定义一个 Agent，一个底座运行一群 Agent，内置 Memory / Tool / MCP / Skill / 知识库 / Notify / Sandbox / Audit。**

它的北极星公式是：

```text
自然语言(md) + Memory + Tool + MCP + Skill + 知识库 + Notify = 一个能干活的 Agent
```

其中：

- **自然语言(md)**：业务方用 `AGENT.md` 定义 Agent，而不是写 Java Agent 后端。
- **Memory**：让 Agent 记住用户、项目和历史决策。
- **Tool**：让 Agent 能读写文件、调 HTTP、跑受控 Shell。
- **MCP**：连接外部工具和企业系统。
- **Skill**：沉淀可复用的约束、流程和专家经验。
- **知识库**：让 Agent 懂企业内部资料。
- **Notify**：让 Agent 到点自动把结果推给人。

## 6. OryxOS 和相邻产品的区别

| 对象 | 产物 | 谁使用 | 跑在哪 | 和 OryxOS 的关系 |
| --- | --- | --- | --- | --- |
| LangChain / Spring AI | 代码库 / SDK | 开发者 | 开发者自建运行时 | OryxOS 复用它们做底层能力 |
| Dify / Coze / n8n | 工作流 | 业务人员 / 开发者 | 平台运行时 | 可运行在 OryxOS 之上或调用 OryxOS API |
| OpenClaw | 个人 Agent OS | 个人 / 小团队 | 本地或自托管 | 同类但定位不同 |
| Hermes Agent | 个人/团队 Agent OS | 高级个人 / 团队 | 本地或自托管 | 同类但非 Java 企业栈 |
| OryxOS | 企业 Agent OS | 企业平台团队 + 业务方 | 企业自己的服务器 / K8s | Java 原生、私有可审计、面向多 Agent 治理 |

## 7. 发展路线

### 阶段一：单机运行时内核

目标是先让一个 OryxOS 实例可靠运行多个 Agent：

- Provider。
- ReAct Loop。
- Memory。
- Tool / MCP。
- Skill。
- Notify。
- REST API。
- SQLite 审计。
- Web 管理台。

### 阶段二：能力版图补齐

补齐公式中的短板和企业使用体验：

- 知识库 + 向量检索。
- 语义记忆。
- 多渠道。
- SSE 流式。
- HITL 审批。
- 成本看板。
- Tool Policy。

### 阶段三：企业级分布式底座

从单机走向企业级部署：

- PostgreSQL / MySQL。
- DB 抢锁调度。
- 多副本。
- 多租户。
- RBAC / SSO。
- Agent 团队协作。
- A2A 跨节点通信。

---

## 8. 调研结论

OryxOS 不是追逐“Agent OS”这个概念，而是锚定一个不会变的企业刚需：

> 企业需要一个自己能完全掌控的 Agent 运行底座。它必须私有部署、数据不出域、工具可控、行为可审计、能接现有系统，并能逐步从单 Agent 走向一群 Agent 的协同。

OpenClaw 和 Hermes 证明方向成立；Java 生态缺位提供了切入口；企业合规、审计和系统集成提供了刚性需求。OryxOS 要做的，就是把 Agent OS 这层能力用 Java / Spring 方式做成企业能用、敢用、能长期治理的开源底座。
