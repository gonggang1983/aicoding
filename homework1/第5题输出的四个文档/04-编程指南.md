# OryxOS AI 编程指南

> 本文基于 `docs/AiProgrammingGuide.md` 与项目当前实践重新整理，目标是指导如何用 AI 编程方式持续开发 OryxOS，同时避免 AI 跑偏项目原则。

---

## 1. 总体策略

OryxOS 适合采用两段式 AI 编程方法：

| 阶段 | 方法 | 适用任务 |
| --- | --- | --- |
| 主体开发 | Spec-Kit / 规格驱动 | 从零搭建核心能力、跨模块大功能 |
| 增量开发 | Claude Code + 手动提示词 | 修 bug、小功能、局部重构、文档补齐 |

核心原则：

> **大功能先写清楚规格，小改动直接让 AI 在现有代码上下文里工作。**

---

## 2. AI 编程的输入文档

每次让 AI 开发 OryxOS 前，应该让它理解四类文档：

1. **业界调研**：说明为什么要做 OryxOS，定位在哪里。
2. **需求分析**：说明要做什么，不做什么。
3. **技术方案**：说明怎么做，模块怎么分，关键边界是什么。
4. **项目指南 / 宪法**：说明绝对不能违反的工程原则。

AI 最容易犯错的地方不是写不出代码，而是没理解边界。

## 3. OryxOS 的非协商原则

每次 AI 编码前都要重复强调：

### 3.1 ReAct Loop 自己实现

不能用 Spring AI 自动 Agent 抽象。

错误倾向：

```java
chatClient.prompt(...).tools(...).call()
```

正确方向：

```text
ProviderService 只调模型
ReActLoop 判断 tool call
ToolExecutor 执行 tool
结果回填 Session
继续下一轮
```

### 3.2 Spring AI 只用协议和 schema

只允许使用：

- Provider 协议转换。
- `@Tool` schema 生成。

不允许使用：

- 自动 tool 执行。
- Spring AI Agent loop。

### 3.3 Provider 显式映射

不能靠 `ChatModel` 类型扫描区分 provider。

必须使用：

```text
provider name → ProviderDef / ChatModel
```

### 3.4 Agent 目录不是 Tool

`.oryxos/agents/<name>/AGENT.md` 是上下文来源，不是可执行 Tool。

- `AGENT.md` 正文由 `ContextLoader` 注入。
- Skill 元数据由 `ContextLoader` 注入。
- Skill 正文通过 `read_file` 按需读取。
- Agent 目录不进 `ToolRegistry`。

### 3.5 审计 day-one 落库

Tool 和 LLM 调用不能只打日志。

必须写：

- `tool_invocations`。
- `llm_calls`。

### 3.6 同步执行模型

核心阶段使用同步阻塞 + Java 21 virtual thread。

不要引入：

- Reactor。
- WebFlux。
- 无必要的 CompletableFuture 编排。

### 3.7 沙箱用白名单，不用 SecurityManager

JDK 21 不使用 SecurityManager。

所有内置 Tool 的 IO 动作必须先过：

```text
Sandbox.enforce(SandboxAction)
```

## 4. 主体开发流程

主体开发建议使用 Spec-Kit 或类似规格驱动流程。

### 4.1 Specify

输入需求分析，生成 feature spec。

OryxOS 可拆成 5 个 user story：

1. Provider：对接 LLM。
2. ReAct：实现 Agent 大脑。
3. Memory：让 Agent 记得住。
4. Tool：让 Agent 能干事。
5. Web Service：对外提供 API。

### 4.2 Clarify

让 AI 针对不清楚的问题发问，例如：

- max_iterations 默认多少？
- max_history_turns 默认多少？
- Tool 失败后中断还是回填？
- Memory 是全局还是 Agent 专属？
- HTTP GET 默认是否需要域名白名单？

澄清后写入 spec，避免实现时反复返工。

### 4.3 Plan

把技术方案转成实施计划：

- 模块结构。
- 数据模型。
- 服务接口。
- 测试策略。
- 验收 Demo。

Plan 必须人工 review，重点检查 AI 有没有违反宪法。

### 4.4 Tasks

把计划拆成小任务：

- 每个任务尽量 1~3 个文件。
- 可以并行的任务标记出来。
- 每个任务都带测试。
- 每个 user story 都有端到端验收。

### 4.5 Implement

执行任务时要遵守：

- 先读现有代码。
- 复用已有工具和接口。
- 先写测试，再修实现。
- 改完跑相关测试。
- 每个 user story 结束跑一致性分析。

## 5. 增量开发流程

主体功能完成后，日常开发采用轻量流程。

### 5.1 推荐步骤

```text
1. 描述问题或需求
2. AI 只读探索代码
3. AI 给出候选方案
4. 选择一个方案
5. 写回归测试
6. 修改实现
7. 跑目标测试
8. 写文档或变更说明
9. review diff
```

### 5.2 修 bug 模板

提示词模板：

```text
在当前 OryxOS 项目中找一个真实 bug。
要求：
- 能用单元测试复现
- 有安全或正确性影响
- 修复边界清晰
- 输出问题、根因、修复方案、测试位置
不要先修改文件。
```

修复时：

```text
请先新增失败测试证明 bug，再修改实现让测试通过。
最后把问题、分析、修复、验证结果写入 bugfix.md。
```

### 5.3 新功能模板

```text
参考 docs/TechnicalSolution.md 和 CLAUDE.md，设计并实现 XXX 功能。
要求：
- 不违反 OryxOS 宪法
- 复用现有接口
- 给出涉及文件
- 加测试
- 跑验证命令
```

## 6. 常见 AI 跑偏点与纠正方式

| 跑偏点 | 表现 | 纠正 |
| --- | --- | --- |
| 使用 Spring AI 自动 tool 执行 | tool 被调两次，审计缺失 | 重读“Spring AI 只用两件事” |
| Provider 靠类型扫描 | 多 Provider 路由错 | 改成 provider name 显式映射 |
| Agent 目录进 ToolRegistry | Agent 被当函数调用 | 强调 Agent 是 ContextLoader 输入 |
| 审计只打日志 | DB 无调用记录 | 强制 `tool_invocations` / `llm_calls` 落库 |
| 过早引入 WebFlux | 架构复杂 | 坚持 Spring MVC + virtual thread |
| 沙箱只做字符串 startsWith | symlink 可逃逸 | 用真实路径校验 |
| CLI 命令启动过重 | 每个查询都启动 Spring | 区分轻命令和重命令 |
| 文档与实现漂移 | docs 说 A，代码做 B | 修改文档或代码，保持一致 |

## 7. 测试策略

### 7.1 单元测试

适合：

- ProfileLoader。
- AgentMarkdown。
- RealPathBoundary。
- WhitelistSandbox。
- FileTools / ShellTools / HttpTools。
- MemoryStore。
- ToolRegistry。

原则：

- 安全模块重点测“绕不过”。
- Tool 模块重点测“校验不过，动作零发生”。
- Parser 模块重点测非法输入。

### 7.2 集成测试

适合：

- ReActLoop + Mock Provider + Fake Tool。
- Session 持久化。
- Web Controller。
- Scheduler 执行历史。
- MCP adapter。

### 7.3 端到端 Demo

至少保留：

- 每日天气。
- 每日科技日报。
- GitHub 日报。

Demo 不是展示用玩具，而是回归验收标准。

## 8. AI 写代码的风格要求

### 8.1 匹配现有代码风格

- Java 21。
- Spring Boot 3.x。
- JUnit 5。
- 中文注释密度与周围一致。
- 命名保持业务语义。
- 不为了“高级”引入复杂模式。

### 8.2 小步提交

每个改动应能解释：

- 为什么改。
- 改了哪些文件。
- 测了什么。
- 风险是什么。

### 8.3 安全默认 fail closed

遇到无法判断的安全边界：

- 不静默放行。
- 不吞异常。
- 给出清晰错误信息。
- 写审计或日志。

---

## 9. 文档维护原则

OryxOS 是文档驱动项目，AI 改代码时也要维护文档。

### 9.1 需要同步文档的场景

- 新增模块。
- 改 Agent 目录结构。
- 改 Tool 接口。
- 改 API。
- 改数据库 schema。
- 改安全策略。
- 改验收 Demo。

### 9.2 不需要同步文档的场景

- 单元测试重构。
- 内部私有方法重命名。
- 小 bugfix 且不改变行为契约。
- 格式化。

### 9.3 推荐文档输出

复杂改动建议写：

- `bugfix.md`：bug 发现、分析、修复、验证。
- `todo/*.md`：规划文档草稿。
- `docs/*.md`：正式文档。

## 10. 推荐提示词清单

### 10.1 探索代码

```text
请只读探索 OryxOS 的 XXX 模块，输出：
1. 当前实现链路
2. 关键类和文件
3. 已实现与未实现
4. 可能风险
5. 测试位置
不要修改文件。
```

### 10.2 设计方案

```text
基于上面的探索结果，设计 XXX 功能实现方案。
要求：
- 遵守 CLAUDE.md 宪法
- 复用现有接口
- 列出要改的文件
- 给出测试策略
- 说明风险与取舍
```

### 10.3 实现

```text
按已批准方案实现。
要求：
- 先改测试或新增测试
- 再改实现
- 跑目标测试
- 如测试失败，如实报告
```

### 10.4 复盘

```text
把本次问题、分析、修复、验证、后续建议写成中文文档。
要求：
- 包含 issue 草稿
- 包含复现步骤
- 包含修改清单
- 包含测试命令和结果
```

## 11. 近期开发优先级建议

结合当前项目状态，AI 编程可以优先推进：

1. **核心收尾**
   - `tool list` 查询真实 ToolRegistry。
   - `provider list` 查询运行时 Provider DB。
   - Flyway 或 schema 版本管理。

2. **知识库**
   - KnowledgeBase 模型。
   - 文档导入和切分。
   - embedding。
   - `retrieve_knowledge` Tool。
   - 管理台。

3. **用户体验**
   - SSE 流式响应。
   - 更好的 Web 管理台。
   - 审计 UI。

4. **企业安全**
   - HITL 审批。
   - API Key / SSO。
   - RBAC。
   - 多租户。

---

## 12. 总结

OryxOS 很适合 AI 编程，但前提是 AI 必须被文档和宪法约束住。

最重要的工作方式是：

> **让 AI 多读文档、先做只读探索、再写计划、最后小步实现并跑测试。不要让 AI 凭直觉重造架构。**

只要守住 ReAct 自实现、Spring AI 边界、Provider 显式映射、Agent 目录不是 Tool、审计 day-one 落库、同步执行模型、沙箱 fail-closed 这几条，OryxOS 就能在 AI 辅助下持续演进，而不会偏离“企业私有可审计 Agent OS”的主线。
