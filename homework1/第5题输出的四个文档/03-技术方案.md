# OryxOS 技术方案

> 本文基于 `docs/TechnicalSolution.md` 与当前项目指南重新整理，目标是回答：OryxOS 应该如何实现一个 Java 原生、私有部署、可审计的 Agent OS 运行底座。

---

## 1. 技术目标

OryxOS 是一个 Java 21 + Spring Boot 3.x 单体应用，通过 Maven 多模块组织。核心目标是：

- 自实现 ReAct Loop。
- 基于 Spring AI / Spring AI Alibaba 做 Provider 协议适配。
- 用 OryxOS 自己的 `ToolExecutor` 执行工具。
- 用 SQLite + 文件系统存储核心状态。
- 用 REST API 和 CLI 对外提供能力。
- 用沙箱和审计保证企业可控。

一句话技术方案：

> **Spring Boot 单体 + 自实现 ReAct + Spring AI 协议适配 + SQLite 审计 + 文件系统 Agent 目录 + MCP Tool 扩展。**

---

## 2. 不可违背的技术原则

### 2.1 自实现 ReAct Loop

OryxOS 必须自己实现 reason → act → observe 循环，不能使用 Spring AI 的自动 Agent 抽象。

原因：

- Tool 调度必须完全可控。
- 审计、沙箱、错误处理都要进 OryxOS 自己的链路。
- 未来要支持 HITL、多 Agent、成本治理和自定义循环策略。

### 2.2 Spring AI 只用两件事

只用：

1. Provider 协议转换。
2. `@Tool` schema 生成。

不用：

- Spring AI 自动 tool 执行。
- Spring AI 的 Agent 抽象。

否则会出现 tool 被调用两次、审计绕过、沙箱绕过等问题。

### 2.3 Provider 显式映射

多个 Provider 并存时，不能靠扫描 `ChatModel` 类型判断 provider。

必须维护：

```text
provider name → ChatModel / ChatModelFactory
```

### 2.4 同步执行 + Virtual Thread

核心阶段全程同步阻塞，配合 Java 21 virtual thread 承载并发。

不引入：

- Reactor。
- WebFlux。
- CompletableFuture 式复杂异步编排。

### 2.5 沙箱不使用 SecurityManager

JDK 21 不再适合 SecurityManager。OryxOS 用应用层白名单作为核心阶段沙箱：

- 文件路径白名单。
- Shell 命令白名单。
- HTTP 域名白名单 + SSRF 防护。

扩展阶段再升级 Docker / SSH / microVM。

### 2.6 审计 day-one 落库

`tool_invocations` 和 `llm_calls` 核心阶段就写入 SQLite，不能只打日志。

## 3. 模块结构

OryxOS 采用 9 个 Maven 模块。

| 模块 | 职责 |
| --- | --- |
| `oryxos-core` | 核心抽象：Profile、Session、AgentLoader、ContextLoader、PromptBuilder、ReActLoop、ToolExecutor、AgentService、AgentScheduler |
| `oryxos-provider` | ProviderService、ChatModel 构建、Function Calling 适配 |
| `oryxos-memory` | MemoryService、Markdown/SQLite/Mem0 MemoryStore、MemoryTools |
| `oryxos-tool` | 内置 Tool、MCP Client、ToolRegistry、Sandbox、Notify |
| `oryxos-channel-cli` | CLI Channel |
| `oryxos-web` | REST API、Controller、GlobalExceptionHandler、Admin 静态资源 |
| `oryxos-storage` | SQLite JPA Entity / Repository / Auditor |
| `oryxos-cli` | Picocli 命令入口 |
| `oryxos-boot` | Spring Boot 启动与 Bean 装配 |

依赖原则：

- core 放接口和领域对象。
- provider / memory / tool / storage / web 实现 core 契约。
- boot 负责装配。
- 不允许循环依赖。

## 4. 整体架构

```text
接入层
  ├─ CLI Channel
  ├─ REST API
  └─ AgentScheduler
        ↓
统一入口 AgentService
        ↓
ReActLoop
  ├─ PromptBuilder
  │   ├─ ContextLoader: AGENT.md + Bootstrap + Skill 元数据
  │   └─ MemoryService: 会话记忆 + 长期记忆
  ├─ ProviderService: LLM 调用
  └─ ToolExecutor
      ├─ ToolRegistry
      ├─ Sandbox.enforce
      ├─ OryxTool.execute
      └─ ToolInvocationAuditor
        ↓
SQLite / 文件系统 / MCP Server / 外部 API
```

核心思想：

- 所有触发源都走同一个 `AgentService`。
- ReActLoop 不关心消息从 CLI、Web 还是 Scheduler 来。
- Provider、Memory、Tool 都通过接口解耦。
- Tool 执行前统一过 Sandbox，执行后统一审计。

## 5. Agent 定义与上下文加载

### 5.1 一个目录 = 一个 Agent

运行时目录：

```text
.oryxos/agents/<agent-name>/
├── AGENT.md
├── skills/        # 指向公共 Skill 的相对软连接
├── scripts/       # 可选脚本
└── REFERENCE.md   # 可选参考资料
```

`AGENT.md`：

- frontmatter：运行配置。
- body：任务指令。

### 5.2 Profile 派生

`AgentLoader` 扫描 `.oryxos/agents/`，读取 `AGENT.md` frontmatter，派生为 `Profile`。

Profile 字段：

- name / description。
- identity。
- provider。
- tools。
- mcp_servers。
- notify_channels。
- schedules。
- bootstrap。
- settings。

### 5.3 ContextLoader

每轮 prompt 组装时：

1. 读取 `AGENT.md` 正文。
2. 读取 Bootstrap 文件：`AGENTS.md`、`SOUL.md`、`USER.md`。
3. 扫描 Agent 本地 `skills/` 绑定。
4. 对已绑定 Skill 只注入 name、description、本地读取路径。
5. Skill 正文由模型后续通过 `read_file` 按需读取。

这样实现渐进式披露：

- L1：Agent 指令 + Skill 元数据。
- L2：模型命中后读 `SKILL.md` 正文。
- L3：再按正文读取参考或运行脚本。

## 6. ReAct Loop 设计

算法：

```text
for i in 1..max_iterations:
  prompt = PromptBuilder.build(session, profile)
  response = ProviderService.chat(prompt, tools)

  if response has no tool calls:
      append assistant message
      return response content

  append assistant tool-call message
  for each tool call:
      result = ToolExecutor.execute(call)
      append tool result message

return max-iterations-exceeded
```

要点：

- 一次响应里的多个 tool call 按顺序执行。
- Tool 失败不直接杀死循环，而是把失败结果回填给模型。
- 达到最大轮数后抛明确异常或返回明确停止信息。
- 每次 LLM 调用写 `llm_calls`。
- 每次 Tool 调用写 `tool_invocations`。

## 7. Provider 技术方案

### 7.1 ProviderService

职责：

- 按 Profile provider name 找到 ProviderDef。
- 构建或复用 ChatModel。
- 把 OryxOS 消息转换为 Spring AI Prompt。
- 把 OryxTool schema 转为 Spring AI function callback。
- 调用底层模型。
- 转回 OryxOS ProviderResponse。

### 7.2 Provider Registry

Provider 配置可来自：

- application.yml 初始配置。
- SQLite 运行时 CRUD。

ProviderDef 字段：

- name。
- baseUrl。
- apiKey。
- model。
- enabled。

### 7.3 Tool schema 适配

`ToolSchemaAdapter`：

- 从 OryxTool 获取 name / description / inputSchema。
- 转成 Spring AI 工具定义。
- callback 不执行真实工具，只做 schema 占位。

真实工具执行必须由 `ToolExecutor` 完成。

## 8. Tool / MCP / Sandbox 技术方案

### 8.1 OryxTool 抽象

```java
interface OryxTool {
    String getName();
    String getDescription();
    JsonSchema getInputSchema();
    ToolResult execute(JsonNode input);
}
```

ToolResult：

- success。
- content。
- errorMessage。
- retryable。

### 8.2 ToolRegistry

注册来源：

1. 内置 Tool。
2. Spring `@Tool` Bean。
3. MCP Tool。

能力：

- register。
- unregister。
- get by name。
- list。
- 按 Profile tools 字段过滤。

### 8.3 内置工具

核心工具：

- 文件：read_file、write_file、list_dir、edit_file、grep、glob 等。
- Shell：shell。
- HTTP：http_get、http_post、http_request、fetch_webpage、download_file。
- Memory：save_memory、recall_memory。
- Notify：notify。
- Utility：current_time、json_extract。
- Web：web_search。
- Interaction：ask_user。

### 8.4 MCP Client

组件：

- `McpConfigLoader`：读写 `.oryxos/mcp_servers.yaml`。
- `McpClientService`：连接 server，拉取 tool list。
- `McpToolAdapter`：把 MCP tool 转为 OryxTool。
- `McpCatalog`：内置常用 MCP server 模板。

### 8.5 Sandbox

接口：

```text
Sandbox.enforce(SandboxAction action)
```

ActionType：

- FILE_READ。
- FILE_WRITE。
- SHELL_COMMAND。
- HTTP_READ。
- HTTP_REQUEST。

WhitelistSandbox：

- 文件：真实路径必须在 allowed roots 内。
- Shell：命令必须在 allowed commands 内，且拒绝组合和替换绕过。
- HTTP 读：默认允许公网，拒绝内网和云元数据地址。
- HTTP 写：必须命中域名白名单。

## 9. Memory 技术方案

### 9.1 MemoryService 门面

对 ReActLoop 暴露统一接口：

- buildContext(session)。
- save / recall。
- readAll。

内部组合：

- Session 会话记忆。
- LongTermMemoryStore 长期记忆。

### 9.2 三档后端

| 后端 | 用途 |
| --- | --- |
| MarkdownMemoryStore | 默认，写 `.oryxos/agents/<name>/MEMORY.md` 或全局 MEMORY.md |
| SqliteMemoryStore | 结构化 memory_entries 表 |
| Mem0MemoryStore | 接自托管 Mem0 做语义记忆 |

### 9.3 注入策略

- 每轮 prompt 重新读取，不缓存。
- 核心记忆完整注入。
- 归档记忆截断注入。
- recall 先关键词，未来升级语义检索。

## 11. Storage 技术方案

### 11.1 SQLite 表

核心表：

- sessions。
- tool_invocations。
- llm_calls。
- scheduled_tasks。
- task_executions。
- agent_executions。
- llm_providers。
- sandbox_whitelist_entries。
- memory_entries。
- notify_channels。

### 11.2 迁移策略

SQLite 的 ALTER TABLE 能力弱，不能长期依赖 Hibernate ddl-auto update。

建议：

- `ddl-auto: none`。
- `schema.sql` 作为当前结构权威。
- 后续引入 Flyway 或等价版本迁移。

### 11.3 文件系统数据

文件系统保存：

- Agent 目录。
- Skill 目录。
- Bootstrap 文件。
- MCP 配置。
- Markdown Memory。
- Agent 输出物。

优点：

- 人可读。
- GitOps 友好。
- 可直接编辑。

## 12. CLI 技术方案

Picocli 命令入口：

```text
oryxos init
oryxos status
oryxos chat
oryxos serve
oryxos gateway
oryxos profile list/create/show/delete
oryxos provider list
oryxos tool list
oryxos session list
```

原则：

- 轻命令不启动 Spring，直接读文件或 DB。
- 重命令启动 Spring 上下文。
- chat / serve / gateway 复用同一套运行时 Bean。

## 13. 定时任务技术方案

`AgentScheduler` 是第三种触发源：

- CLI / Web 是人推。
- Scheduler 是钟推。

实现：

- Spring `TaskScheduler`。
- `CronTrigger`。
- `ReentrantLock` 防止同一任务进程内重叠。
- `ScheduledTaskStore` 持久化状态。
- `TaskExecution` 记录执行历史。

调度执行时仍调用 `AgentService.process()`，不复制 ReAct 逻辑。

## 16. 技术结论

OryxOS 的技术方案核心不是堆功能，而是守住几个边界：

1. ReAct 自己写。
2. Spring AI 只做协议和 schema。
3. Tool 执行必须经过 OryxOS 的沙箱和审计。
4. Agent 是目录，不是 Tool。
5. Skill 是约束与知识，不是可执行函数。
6. 核心阶段同步阻塞，靠 virtual thread 承载并发。
7. 数据与审计留在企业自己的基础设施。

守住这些边界，OryxOS 才能从单机运行时内核自然演进到企业级 Agent OS。
